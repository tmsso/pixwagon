# Repo review — 2026-09-16

A full-repo review against intended purpose, progress, design choices, structure, documentation, completeness and delivery trajectory. Written so that the usual Sonnet-with-Opus-advisor sessions can pick up the next batches with less re-derivation. Findings are grouped by what to do about them; items marked **fixed** were changed in the same PR as this document.

## Verdict in one paragraph

The project is in good shape and on its original trajectory. The architecture's load-bearing rules (pure `game-core`, protocol separate from rules, derive-don't-advance RNG, hibernation-first Durable Object, packs as data) have all held through nine PR-batches, and the tests genuinely lock the contracts they claim to lock. The main problems are not in the code. They are (1) the plan document had turned into a delivery diary that a fresh session has to read in full to find the plan, (2) three phases are Delivered-but-not-Accepted because their Accept lines need a phone, and nothing batched those checks into one owner step, and (3) Phase 5 cannot start because the meaning of "same board" is contradicted between the architecture doc, the game-core types, and the pass-02 design surfaces. All three are addressed in the rewritten `ROADMAP.md`.

## What is good and should not be touched

- **`packages/game-core`** is small, pure, well-commented and property-tested. `applyMove` is the single legality function both sides run; the bijective pair check and the compound-face both-or-nothing rule are exactly right. The frozen-snapshot discipline on `rng.ts` and `shapes.ts` is the right tripwire.
- **`packages/protocol`** validates inbound with zod and keeps the "shape here, meaning in game-core" split consistently (`pieceId` as string, `fallbackFaceSchema` mirrored with a drift test in the one package that sees both).
- **`apps/server/roomState.ts`** pulled the room decisions out of the Durable Object glue so they test in plain Node. Keep doing this for Phase 5: fills and round advance belong in `roomState.ts`, not `room.ts`.
- **`apps/web/src/state/`** mirrors that pattern (`placement.ts`, `legality.ts`, `offerView.ts` pure; the store is the only thing touching React). The exact blob-enumeration legality check is the correct call over a heuristic, and its comment records why.
- **Verification culture**: `pnpm verify` and CI run the same eight steps; generated files are drift-checked; the achievability seed is replayed through the store's public actions. 187 tests, all green locally and on `main` at review time.
- **Privacy hygiene** has been applied consistently (subdomain rename, bare Pages name, no `account_id` in config, name grep). No leaks found in a repo-wide grep this review.

## Code-quality notes (not fixed; none urgent)

- `apps/server/src/room.ts` `#handleJoin` allows a joined socket to re-`join` with a new name but does not re-broadcast presence with the new name until the next event. Fine until a rename UI exists.
- `apps/web/src/state/soloGame.ts` `passRound` has no guard against `status === 'complete'`; the UI never offers it then, but the store is the contract. One line when next touched.
- `apps/web/src/state/legality.ts` `pairHasLegalPlacement` is quadratic over legal placements of both pieces. Boards are a few hundred cells; fine. If Phase 6 adds larger pictures, memoise per roll.
- `apps/server/src/index.ts` `POST /api/room` does not check whether a code is already in use. With 32⁴ codes and rooms that persist storage after emptying (by design), a collision resumes a stale room. Acceptable for a hobby tier; a `POST` that peeks at the DO's storage is a five-line Phase 5 improvement.
- No rate limiting anywhere. Acceptable on the free tier's own 100k/day cap; note it in Phase 9 if the app is ever shared publicly.
- `packages/packs/src/index.ts` registers packs by hand (`packs = [transportation]`). That is the one known leak in the "adding a pack is one file" claim; Phase 8 will hit it. A `data/index.json` manifest fixes it.
- Component tests render through `renderToStaticMarkup` and assert on strings (no jsdom). That is a deliberate, documented choice and has been enough so far. The Phase 4 client half will need behavioural tests for the store and transport, not for components; keep it that way.

## Plan and scoping problems (addressed in the new `ROADMAP.md`)

1. **Same-board semantics are contradictory** (D1 in the roadmap). Architecture §1 and `game-core` assume per-player copies of one picture; pass 02's provisional surfaces assume one contested board with first-claim toasts. Under the contested model, all-or-nothing scoring per picture has no per-player meaning, `Board` needs a per-cell owner, and latency becomes gameplay — the exact unfairness the mechanics correction removed from the fallback reveal. Recommended: per-player copies. This is the owner's call because the design depicts the other.
2. **Turn model was never written down** (D2). Simultaneous rounds with auto-advance is the simplest thing consistent with the host-only roll issuance already built.
3. **Session end was decided but not scheduled.** "Cycles through the pack, ends on a precomputed round budget" (Phase 1, 2026-08-01) appears in no phase's deliverables. Now: one picture per session in Phase 5, cycling in Phase 6, with a concrete budget formula to overrule if wanted (D3).
4. **Phase 4's remaining half needed a real spec.** "Client WebSocket layer with reconnect and resync" is one line in the old roadmap; the identity problem on reconnect (fresh `playerId` and seat) would have been discovered mid-batch. Now five ordered deliverables with done-criteria, including a rejoin token.
5. **Phase 7 conflated two things.** The daily seed is a date string fed to the existing solo store and needs no server or storage; persistence is a separate decision. Split into 7a/7b.
6. **Accept lines that need devices** were blocking the narrative without blocking the work. Now one owner-run checklist, and the status table shows "delivered / accept pending" honestly.

## Operating recommendations for the next sessions (Sonnet + Opus advisor)

- **Read order for a fresh session:** `CLAUDE.md` → `ROADMAP.md` status table and the phase being worked → that phase's "Decided" lines in the relevant `docs/contracts/*.md` → only then `docs/delivery-log.md` for the specific history you need. Do not read the delivery log end to end.
- **Batch shape:** one PR per numbered deliverable in the roadmap, in the listed order. The "Done means" list is the PR checklist. Ask the D-decisions in one message at the start of the batch, not one at a time.
- **Verification bar:** `pnpm verify` green locally, CI green on the PR, and — for anything touching the server — a `wrangler dev` two-tab check written up in the PR body with what was actually observed. Never write a verification result before the step ran (already learned once, `7c9aed3`).
- **Deploys:** `wrangler pages deploy` may be run after explicit confirmation; `wrangler deploy` (the worker) is owner-run. Say so in the PR body when a merge leaves the live worker behind `main`.
- **Design sync:** any new component with a preview card (`BoardCompare`, `ConnectionPill` in Phase 5/6) goes through `pnpm design:build` → `pnpm design:check` → `/design-sync` before the next design pass, and Claude-Design-sourced content gets the real-name grep like everything else.
- **When to escalate above Opus:** a change to the RNG derivation, the shape library, or the `same-board` model after D1 is decided — these silently invalidate every seeded room and daily puzzle. Everything else in the plan is Sonnet-grade work.
